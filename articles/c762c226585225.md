## はじまり：X の投稿から、ミューに「手足」を付けた

始まりは、検索の話ですらありませんでした。

11月1日の夜、X で見た投稿をミューに貼って「どう言うこと？」と聞きました。家の Windows パソコンを、Tailscale と SSH とブラウザ操作の MCP で、クラウドの AI の「手足」にする、という話です。

面白そうなので、やってみました。11月4日の昼から夕方にかけて、家の Mac Studio と、今は動画を流すだけになっていた古い Windows パソコンを、ミューの手足にしました。Tailscale で同じ仮想のネットワークに入れ、SSH で入れるようにし、再起動しても、ブラウザ操作の MCP サーバーが自動で起動し直すことまで確かめました。

その途中で、家の NAS も、とっくに同じネットワークに入っていたとわかります。ミューの鍵を NAS に登録すると、ミューから SSH でファイルの一覧が取れました。

それまで私は、リモートデスクトップで家のパソコンにつなぎ、そこのブラウザから NAS の画面を開いていました。画面の中の画面です。それが、ミューからは SSH で直接届くようになりました。

届くようになったところで、次の疑問が出ます。**ミューは、NAS の中を検索できるのか？**

ミューに測ってもらうと、`find` でのファイル名の検索は、約 169 万ファイルを全部たどって 12〜15 秒。意外に速い。でも本文の検索は、そのたびに全部のファイルを読むことになるので、現実的ではありません。先に索引を作っておく形が要ります。

そういえば、NAS には検索のアプリがあったはずです。

## 1日目の夜：ミューと話し、ChatGPT に調べさせる

11月4日の 19時22分、ミューにこう聞きました。

> あとは、NAS に Universal Search を入れておこう。ただ、これは SSH から利用できるのか？

ミューは NAS を調べて、答えを2段で返してきました。

- Universal Search は、もう入っていて動いている。ただし索引の中身は約 2.8MB で、ほぼ空。どのフォルダを索引にするか、決めていなかったからです
- SSH からは、そのままでは使えない。`synosearch` という名前のコマンドはあるが、中身は DSM のヘルプを検索するもので、別物

ここから、2つの AI の間を行ったり来たりしました。調べ物は ChatGPT が得意なので、ChatGPT に調べさせます。その答えをミューに見せ、ミューの意見を ChatGPT に返します。

- ChatGPT は「検索エンジン（sist2）を足して、その上に MCP サーバーを置く」案を出した
- ミューはそれを読んで、骨組みは妥当だと評価した。ついでに、ChatGPT が「弱い NAS」を前提にしていることを指摘した。実は、ミュー自身の記録も NAS の機種を古いものと取り違えていて、その日に直していました
- 私が「GitHub に Synology の MCP があるんじゃないのか？」と聞くと、ミューはいくつも見つけてきた。ただ、どれもファイル名の検索が中心で、本文の検索は Universal Search の索引しだいだった

ここで大事な区別がつきました。**MCP は AI と検索をつなぐ口で、MCP を入れても検索は速くならない。** 速さは、検索の中身（索引）で決まります。

そこで、索引は Universal Search のものをそのまま使い、そこに AI から届く口を作る、という方向に決まりました。

## 1日目の夜：ミューと作った、sudo が要る試作

ChatGPT は、先に作られた例を見つけてきました（atkaper/synology-universal-search-cli、2021年）。NAS の中の `synowebapi` というコマンドで、Universal Search の検索 API を呼ぶものです。この結論をミューに渡すと、ミューは NAS で確かめて、その API が今の DSM 7.4 にも実在することを確認しました。

私が「メンテされてないのか？」と聞くと、ミューは調べて答えました。最後の更新は 2021年5月8日で、それから5年以上止まっている。だから、**スクリプトは使わず、「この API を呼べば索引が引ける」という知見だけをいただく**。この方針は、最後まで変わりませんでした。

問題は、`synowebapi` が root しか動かせないことです。ミューに「root のシェルで、この1行を貼ってください」と頼まれて、私が打ちました。

- 1回目：`success: true`、0件。DSM の画面を見ると「インデックス付きフォルダ：なし」。索引が空だったのは、対象のフォルダを1つも決めていなかったからでした
- 小さな共有フォルダを1つ索引にして、もう一度：47件。名前にもパスにもその語を含まない PDF も返ってきた。本文まで索引ができているらしい（本文で見つかることをはっきり確かめたのは、あとで作ったデモの資料です）

これで「Synology の索引が、そのまま AI の検索エンジンになる」とわかりました。

ミューはそのまま、試作を形にしました。root の持ち物の「検索だけをするラッパー」を NAS に置き、sudo で「このラッパーだけはパスワードなしで実行してよい」と許す形です。設置のスクリプトはミューが用意し、私が root で貼りました。最後の文法チェックの `visudo` が DSM に入っていなくて少し慌てましたが、20時06分、ミューの仮想マシンから検索が通りました。

ちなみに、このラッパーの名前は `nas-search` でした。今のツールで、エージェント側のコマンドに付いている名前と同じです。

正直に書くと、この試作を誰が作ったのか、私は覚えていませんでした。ChatGPT が書いた気がしていたのです。ミューの記録を読み返して、やっと「設計と実装はミュー、調べ物は ChatGPT」と言えるようになりました。2つの AI と行ったり来たりしていると、たった4日前のことでも、どちらと話したのかがわからなくなります。

## 1日目の夜：「sudo なしでできれば」

動いたのですが、私は ChatGPT にこう言いました。

> sudo つかわずに検索できれば、いいだけどねぇ。

これが分かれ目でした。ミューの出番は、ここでいったん終わります。ここから先、sudo のいらない版は、ChatGPT と、あとで加わるクロとの間で作りました。

ChatGPT と、DSM の Web API を一般ユーザーで呼ぶ道を探しました。DSM の画面が裏で使っている HTTP の API です。NAS の中から、一般ユーザーのまま `https://127.0.0.1:5001/webapi/` に `SYNO.API.Info` を問い合わせると、同じ検索の API が Web API の入口からも呼べるとわかりました。そこからは、エラーを1つずつつぶす作業です。

- 認証なし：エラー 119
- 普通のログイン：エラー 403（2段階認証のコードが要る）
- コード付きでログインできたが、検索はエラー 119、条件を変えると 120
- ログインの種類を `FileStation` に替え、検索の条件をそろえると、**通った**

`test` で 1,333 件。一般ユーザーで、sudo なしで、2段階認証も外さずに、です。

あとでミューがまとめてくれた言葉が、いちばん正確です。

> root が要るのではなく、root が要る道具しか知らなかった。

API を使えるかを決めていたのは、Unix の root ではなく、DSM のログインでした。

ただ、ログインには2段階認証のコードが要ります。AI に毎回コードを打たせるわけにはいきません。そこで、のちに「人が1回ログインして検索セッションを始め、そのセッションをメモリに持つ小さなプロセスを、AI は検索のためだけに使う」形にしました。AI はパスワードもコードも持ちません。くわしくは、前の記事に書いています。

## 1日目の夜：Codex を入れようとして、やめた

ここで ChatGPT は「あとの実装は Codex で」と勧めてくれました。いちばん難しい「API にどう届くか」は解けていて、残りは普通のソフトウェアの仕事だからです。

ChatGPT が、GitHub と連携して、新しいリポジトリに最初の CLI と文書を3つ直接入れてくれました。

- `README.md`：人向けの説明
- `AGENTS.md`：AI 向けの作業の決まり
- `docs/verification.md`：実機で何を確かめたか

20時49分のことです。19時22分にミューへ「SSH から使えるのか？」と聞いてから1時間半ほど、ミューの sudo の試作を NAS に置いた 43 分後でした。

続いて、Mac にリポジトリを取ってくるところでつまずきます。GitHub の鍵のエラーです。これは `gh` で解決しました。そのあと、Codex のアプリにするか CLI にするかを話しているうちに、私はこう言いました。

> Claude Desktop で行うことにしたい。マシンの空き容量が少なくて、Codex やアプリを入れるのは避けたいから。

Codex がだめだったのではありません。**Mac の空き容量**の都合です。

クラウド版の Claude Code ではなく手元の Mac にしたのは、実装しながら家の NAS で試す必要があったからです。手元の Mac は Tailscale で NAS に届きますが、クラウド版からは届きません。

## 1日目の夜〜3日目の朝：クロが作り、ChatGPT が見る

21時すぎ、Claude Desktop の Code タブで、クロに引き継ぎました。渡したのは、GitHub のリポジトリ（CLI と文書3つ）だけです。会話の履歴は渡していません。

私がクロに最初にした質問は「Desktop Commander など必要か？」でした。要りませんでした。

クロは1時間足らずで、最初の CLI をテストできる形に作り直しました（v0.2.0、21:47 に取り込み）。翌日の夜には、v0.7.0 まで進みました。

- 人が1回ログインして「検索セッション」を始め、AI はセッションを使って検索するだけ
- AI 用の SSH 鍵は、検索の入口しか動かせない（`authorized_keys` の `restrict,command=`）
- 検索専用の DSM アカウントで、見える範囲を絞る

### 公開するために、リポジトリを作り直した

2日目の朝、自分用の CLI がひととおり動いたところで、公開しようと思い立ちました。クロに「固有名詞はどう扱えばいいか」と聞くと、クロはまずファイルと履歴を全部洗い出しました。

見つかったのは、思ってもみなかったものです。**コミットの作者の欄に、私の本名と職場のドメインが入っていました。** Mac の git にメールアドレスを設定していなかったので、Mac の名前から自動で作られていたのです。NAS の名前や IP も、30 か所ほど残っていました。

ファイルを直しても、履歴には残ります。そこで、**履歴を持たない公開用のリポジトリを、別に作り直しました。** 名前や IP は `<nas-host>` のような置き換えの文字にして、作者の欄は GitHub の匿名のアドレスにしました。自分用のリポジトリは、非公開のまま残っています。

これで終わりではありませんでした。3日目の朝、公開の準備の途中でもう一度調べると、新しい履歴にも本物の共有フォルダの名前が残っていました。まだ非公開で、使っているのは私の Mac とミューだけだったので、履歴をもう一度書き直しました。

公開は、作り直したほうのリポジトリで仕上げました。

### ChatGPT がレビューする

この間、ChatGPT はレビュー役でした。クロの「直しました」をそのまま信じず、GitHub のコードを読み直して、穴を見つけます。

- 50件だけ欲しいときに、51〜100件目が抜けて、次は101件目から読んでしまう
- 結果から範囲の外のファイルは消していたが、ページの番号から「範囲の外にも何かある」とわかってしまう
- 待ち時間が食い違っている。検索を打ち切る時間、SSH の入口が待つ時間、エージェント側が待つ時間がかみ合わず、検索が終わる前に入口が切れることがあり得た

どれも、私の普通の使い方ではまず気づかないものでした。クロが直し、同じ穴が開かないようにテストを足しました。

## 3日目：ミューと戸締まり

3日目の午後、ミューの仮想マシンにも、検索しかできない鍵を置きました。今いちばん使っているのは、実はこの形です。クラウドの AI が、Tailscale を通って、家の NAS を検索します。

あわせて、戸締まりをしました。

## 3日目の夜〜5日目：0.7 のつもりが 0.8 に、そして 0.9 を先に

公開の準備は、もともと 0.7.0 で進めていました。名前を `unisearch` に替え、NAS で一通り確かめた版です。

ところが、英語の README を作っているうちに、コマンドのメッセージが日本語だけなのが気になりました。英語で読みに来た人が、日本語のエラーを見て困る。そこで、英語でもメッセージを出せるようにした 0.8.0 を作り、**公開するのは 0.8.0 にしました。** 0.7.0 は、一度も外に出ていません。

もう1つ、気になっていました。**CLI だけだと、反応が悪そうだ。** 今の AI の道具は、MCP で使うのが当たり前になりつつあります。シェルを使えないアプリからは、CLI は使えません。

そこで、0.8.0 を出す前の夜に、MCP サーバーを足した 0.9.0 を、別のブランチで先に作っておきました。中身は、CLI をそのまま呼ぶ小さなサーバーです。ただ、0.8.0 の確認をやり直したくなかったので、0.8.0 を出すまでは、main には入れませんでした。

4日目の夕方、0.8.0 をベータとして公開しました。Zenn と X にも書きました。

翌朝（5日目）、ミューに「GitHub の反応がない」とこぼしたところから、ミューが監督役になります。ミューは、ブランチで寝かせていた 0.9.0 を読んで、穴を4つ挙げました。

1. README で MCP が見えない
2. MCP のカタログに載せるためのファイル（MCP Registry 用の `server.json`、Glama 用の `glama.json`）がない
3. Claude Code 以外のアプリで試していない
4. 最初に出る README が日本語

この日のうちに、全部埋めました。リポジトリの名前を替え、英語の README を先頭にし、Claude Desktop で試し、PyPI と MCP Registry に載せて、0.9.0 を出しました。0.8.0 の公開から、1日後です。

## 試作は1時間半、公開版は3日半

振り返って、いちばん実感したのは、試作と公開版にかかる時間の差です。

| 段階 | かかった時間 | 中身 |
|---|---|---|
| 自分用の試作 | 約1時間半（11月4日 19:22〜20:49） | root を使う試作、sudo なしで検索が通る、最初の CLI |
| 自分用に動く CLI | 翌朝まで | テストできる形に作り直す（テスト 30 件） |
| 公開版 | 約3日半（11月5日の朝〜8日の昼） | 0.8.0 の公開、0.9.0（MCP）、PyPI、MCP Registry（テスト 162 件） |

公開版に手がかかったのは、「自分は知っている」ことを、全部外に書き出す仕事だったからです。

- **自分なら気にしないこと**：履歴に、本名や NAS の名前が残っていた。リポジトリを作り直し、もう一度書き直した
- **自分の使い方では起きないこと**：ページ送りの抜け、範囲の外の件数が漏れる、待ち時間の食い違い。他の人が使う前提で、初めて問題になった
- **自分は知っているので、要らなかったもの**：README、英語、スキル、変更の記録、セキュリティの窓口、デモの GIF、確かめたことの記録
- **自分の環境では、要らなかったもの**：`pip` で入る形、MCP、Claude Desktop での確認。PyPI には4回目で出せた

自分だけがわかればいいものを、多くの人がわかるようにする。そちらのほうが、ずっと手がかかります。AI のおかげで試作は1時間半で済みましたが、公開の手間は消えませんでした。試作が速くなったぶん、その差がよく見えるようになったのだと思います。

## 泥縄だったところ

振り返ると、予定どおりに進んだことはほとんどありません。

- 検索アプリを足すつもりが、既にある索引を使う話になった
- 検索させる範囲も、あとで替えた。最初は `homes` を索引にしたが、検索専用のアカウントに `homes` を読ませると、全員のホームフォルダが結果に出るとわかった。DSM の権限では1人分だけを許せないので、検索させたいファイルを別の共有フォルダに移した
- MCP を作るつもりが、まず CLI になった（MCP は最後に足した）
- 0.7.0 で公開するつもりが、英語を足した 0.8.0 で公開した。0.9.0 は、0.8.0 の公開より先にできていた
- sudo の形で動いたのに、作り直した
- Codex で作るつもりが、空き容量の都合で Claude になった
- コマンドの名前を、途中で替えた（`synosearch` → `unisearch`）。DSM に同じ名前の別のコマンドがあったからです。最初のころのミューのメモには、そのことがもう書いてありました
- 公開するために、リポジトリを作り直した。公開の準備の途中で、その履歴もまた書き直した。公開したあとには、名前も替えた
- PyPI に出すのは、4回目でやっと通った。リポジトリが外部の Action を許さない設定だった、`~/.ssh` がないと失敗するテストがあった、フォルダの名前が Python の部品の名前とぶつかった。この3つで止まった
- AI の側も間違えた。ミューは古い写しを読んで、ずれた指摘をした。ChatGPT のまとめには、書き直す前の古いコミットの番号が並んでいた

役割分担も、最初から決めていたものではありません。頼んで、見せて、また頼むうちに、形になりました。

## それでも崩れなかった理由

泥縄でも、崩れずに済んだのは、次の4つがあったからだと思います。

**1. 決まりを、最初に書いておいた。**
`AGENTS.md` の最初の版に、こう書いてありました。sudo や root を求めない。2段階認証を外さない。パスワードやコードを、コードにもログにも残さない。まだ確かめていないことを、できたと書かない。どの AI に替わっても、この決まりは変わりませんでした。

**2. GitHub が、共有の記憶になった。**
AI どうしは話していません。それでも、コードと `docs/verification.md` を見れば、誰でも今の状態を確かめられました。だから、途中で AI を替えても、何も失いませんでした。

**3. 「確かめた」と「まだ」を、分けて書いた。**
`verification.md` は、確かめたことと、まだ確かめていないことに分かれています。AI が「直りました」と言っても、記録に戻って確かめられました。間違いが出ても、そこで止まれました。

**4. 最後の鍵は、人が持った。**
パスワードと2段階認証のコードは、いつも私が打ちました。root での作業、push の許可、公開、投稿のボタンも、私です。AI には、検索しかできない鍵だけを渡しました。

## 私がしていたこと

まとめると、私は3つの AI の間に立って、こういうことをしていました。

- 誰に何を頼むかを決める
- ある AI の報告を、別の AI に見せる
- 方向を変えるときに、決める（「sudo なしで」「先に 0.8 を出す」「名前を替える」）
- 人にしかできない作業をする
- 調査、実装、監査を、別の AI に分ける。乗り換えるのは区切りのよいところ

オーケストレーションと言えば聞こえはいいのですが、実際は、手で運んでいました。

## 1つだけ、意識してやっていたこと

泥縄の中で、1つだけ意識していたことがあります。**どこで AI を乗り換えるか**です。

1つの AI に、あれもこれもやらせると、会話の中身（コンテキスト）が濁ります。調べ物の途中の迷い、試して捨てた案、別の話題。そういうものが混ざるほど、答えの精度が落ちる。そう感じていました。

そこで、調査や監査は、実装とは分けました。

- **調査**は ChatGPT に頼んだ。ミューやクロが実装の途中で調べ物を始めると、その会話が調べ物の話で埋まってしまう
- **実装**はクロに任せた。引き継ぐときに渡したのは、GitHub のリポジトリだけ。それまでの迷いは渡していない
- **監査**（できたものを外から見直す役）は、作った AI とは別の AI に頼んだ。初めは ChatGPT、終わりのほうはミュー。作った本人は、自分の作ったものの穴に気づきにくい

乗り換えるのは、区切りのよいところにしました。調べ終わって方針が決まったとき。試作が動いたとき。1つの版ができたとき。そういうところで、わかったことを GitHub の文書に書き出してから乗り換えると、次の AI は、きれいなコンテキストから始められます。

「GitHub が共有の記憶になった」と前に書きましたが、裏返すと、**GitHub に書き出せるところが、乗り換えどき**でした。

## わからないこと

ChatGPT のレビューで、いくつも穴が見つかりました。それが「別の AI だったから」なのか、「作った人とは別の立場で見たから」なのかは、この1回だけではわかりません。たぶん、後者の効き目が大きいと思っています。

## おわりに

作ったものは、小さな検索ツールです。それでも、日曜プログラマが5日で、テストと実機の記録がそろったものを出せたのは、AI と組んだからです。

ただ、AI に任せきりにしたわけではありません。何を守るかを先に書き、記録を残し、区切りのよいところで乗り換え、鍵を手放さなかった。泥縄でも、それさえ守れば、なんとかなる。それが、今回いちばんの学びでした。

忘れないうちに、書いておきます。
