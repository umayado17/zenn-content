NAS に何十万もの資料があって、AI エージェントに「あの資料どこだっけ」を探してほしい。でも、エージェントに root を渡したくはない。

そこで、Synology NAS の **Universal Search がすでに作っている全文検索の索引**を、SSH 経由で AI エージェントから使えるようにする小さなツールを作りました。MCP サーバーとしても、コマンド（CLI）としても使えます。

:::message

作り方の記録（3つの AI を渡り歩いた5日間）は、[別の記事](https://zenn.dev/n_hiraoka/articles/c762c226585225)に書きました。

ポイントは3つです。

- **索引はもうある**：検索エンジンを新しく立てません。Synology が作って、手入れもしている索引を使います
- **渡すのは検索だけ**：sudo も root も要りません。DSM の2段階認証もそのままです。エージェントはシェルにも、パスワードにも触れません
- **Python の標準ライブラリだけ**：NAS 側は1ファイルを置くだけです

この記事では、なぜこの形になったのかと、どこまで実機で確かめたかを書きます。

:::message alert
Synology が公開していない Web API（`SYNO.Finder.FileIndexing.Search`）を使っています。DSM の更新で、予告なく動かなくなるおそれがあります。Synology 社とは関係のない、非公式のツールです。
:::

## 全体は3つの層

| 層 | 中身 |
|---|---|
| 接続 | エージェントから NAS に SSH で届く道。私は Tailscale を使っています |
| 索引 | Universal Search が作る全文検索の索引 |
| 権限 | 検索専用の DSM アカウントと、検索しかできない SSH 鍵 |

私の環境では、AI エージェントはクラウドの仮想マシンで動いていて、NAS は家の LAN の中にあります。仮想マシンと NAS を Tailscale で同じネットワーク（tailnet）に入れて、SSH が届くようにしました。NAS のポートはインターネットに開けていません。ツール自体は Tailscale がなくても、SSH が届けば動きます。

## find と grep では足りない

エージェントは SSH で NAS に入れます。ただ、`find` や `grep` は、検索のたびにファイルを全部たどります。

- ファイル名の検索（`find`）は、思ったより速いです。私の環境では、約169万ファイル・1.76TB を全部たどって12〜15秒でした
- 本文の検索（`grep`）は、毎回すべてのファイルを読みます。データが大きいと使えません

欲しいのは逆の形です。NAS があらかじめ索引を作っておき、エージェントは索引に問い合わせる。返ってくるのは名前・パス・更新日などの短い情報だけで、中身を読むのは必要なファイルだけ。

つまり、やりたいのは「検索エンジンを作ること」ではなく、「**すでにある索引を、AI から使えるようにすること**」でした。

## Universal Search：よい索引があるのに、プログラムからの入口がない

Synology の Universal Search は、DSM 7 では通常、最初から入っています。指定した共有フォルダについて、ファイル名だけでなく文書の本文まで索引にしてくれます。

ところが、これをプログラムから使う公開された入口がありません。SSH の普通のコマンドは、この索引を使いません。

もう1つ落とし穴がありました。**索引を作るフォルダを指定しないと、索引は作られません。** 私の NAS でも、パッケージは動いているのに、対象のフォルダが0件で、索引は約2.8MB しかありませんでした。「入っているのに検索できない」原因はこれでした。設定は、Universal Search の環境設定の「ファイルインデックス処理」にあります。

![Universal Search の環境設定。ファイルインデックス処理のタブに、インデックス付きフォルダの一覧と状態が出ている](https://raw.githubusercontent.com/umayado17/synology-search-agent/main/docs/images/universal-search-indexing-ja.png)
*「ステータス」が「終了」なら、索引はできあがっています（フォルダ名は伏せています）*

自分で全文検索の索引を作る案（sist2 や SQLite FTS5 など）も考えました。でも、索引を2つ持つと、CPU も保存場所も手入れも2倍になります。使える索引がすでにあるなら、まずそれを使うことにしました。

## 内部の API を呼ぶと、索引がそのまま検索エンジンになった

DSM の内部には、索引を検索する API `SYNO.Finder.FileIndexing.Search` があります。本文にも重みをつけて検索でき、結果はパス・名前・サイズ・更新日を含む JSON で返ります。

この API を呼び出せることは、[atkaper/synology-universal-search-cli](https://github.com/atkaper/synology-universal-search-cli)（2021年）で知りました。あちらは2021年から更新されておらず、ライセンスも付いていないので、コードは使っていません。参考にしたのは「この API があって、呼び出せる」という点です。

実機で試すと、ある英単語で、名前にその単語を含まない文書も、本文が一致して返ってきました。これで「Synology の索引を AI の検索エンジンとして使える」と分かりました。残った問題は権限だけです。

## 権限：root を渡さず、検索だけを渡す

### 最初の形（やめた）

最初は、試すときに使った `synowebapi`（root しか実行できない）を呼ぶラッパーを root の持ち物として置き、sudo で「このラッパーだけパスワードなしで実行してよい」と許可しました。

動きはしましたが、弱いところが残りました。

- 置くときに root の作業が要る
- DSM を更新すると、sudo の設定が消えるおそれがある
- 特権で動くプログラムが1つ増える

なので、特権を使うこと自体をやめました。

### いまの形

同じ API を、DSM の Web API（`https://127.0.0.1:5001`）から**一般ユーザーとして**呼びます。ただし、ログインには2段階認証のコードが要るので、エージェントだけでは呼べません。そこで、「ログインは人がして、検索はエージェントがする」形にしました。

```
AIエージェント ──ssh（検索専用の鍵）──▶ NAS: unisearch --agent-gateway
   nas-search                                   │（UNIXソケット）
                                                ▼
                                     検索セッション（人が OTP で開始）
                                                │
                                                ▼
                                     DSM Web API（127.0.0.1:5001）
```

- **検索セッション**：人が SSH で入って、検索専用の DSM アカウントのパスワードと2段階認証のコードを入力します。ログインの結果（SID）は、そのプロセスのメモリの中だけに置きます。ファイルにもログにも残しません。期間は既定で8時間、最大90日です
- **検索専用の鍵**：エージェントの SSH 鍵は、`authorized_keys` の `restrict,command=` で、検索の入口しか動かせません。シェルにも入れず、ポート転送もできません
- **検索専用の DSM アカウント**：管理者にせず、2段階認証をかけ、検索させたい共有フォルダだけを読めるようにします。範囲の守りの中心は DSM の権限で、CLI の `--allow-prefix` はその補助です。範囲の外に何件あったかも、結果に出しません

エージェント側からは、こう使います。

```bash
nas-search "在留資格 申請" --limit 20
```

```json
{"schema_version": 1, "query": "在留資格 申請", "offset": 0, "limit": 20, "total": null,
 "returned": 20, "next_offset": 20,
 "hits": [{"name": "....pdf", "share_path": "/archive/....pdf", "size": 12345,
           "is_dir": false, "modified_utc": "2014-04-05T08:15:21Z", "...": "..."}]}
```

セッションが切れていれば、終了コード 8 が返ります。エージェントは自分でログインしようとせず、「NAS の検索セッションを始めてください」と人に頼みます。Claude Code 用のスキル（説明書）も同梱しています。

### MCP サーバーとして使う（v0.9.0〜）

シェルを使えないアプリ（Claude Desktop など）からは、MCP サーバー `nas-search-mcp` として使えます。道具は `search` と `status` の2つだけで、中身は `nas-search` を呼んでいるだけです。鍵も、検索できる範囲も、返る JSON も同じです。

```bash
claude mcp add nas-search -- uvx nas-search-mcp
```

Claude Desktop のように設定ファイルに書くアプリでは、こう書きます。

```json
{"mcpServers": {"nas-search": {"command": "uvx", "args": ["nas-search-mcp"]}}}
```

- アプリがシェルの `PATH` を見ない場合は、`command` を `which uvx` で出るフルパスにします
- 職場など、HTTPS を中継するネットワークで `uvx` が `invalid peer certificate: UnknownIssuer` で失敗する場合は、`args` の先頭に `--system-certs` を足します（作者の職場の Mac がこれでした）

## 実機で確かめたこと

Synology DS225+（DSM 7.4.1）で、次を確かめました。

- SSH を閉じたあとも、検索セッションは動き続ける
- エージェントの鍵で `ls` などを頼んでも、終了コード 2 で断られる
- 2台のマシン（手元の Mac とクラウドの仮想マシン）から、それぞれ検索専用の鍵で検索できる
- 検索専用アカウントが読めない共有フォルダのファイルは、結果を最後のページまでたどっても1件も出ない
- 20件ずつのページ送りと、まとめて300件取った結果が、重複なく同じ順番になる
- MCP サーバー（v0.9.0）で、Claude Desktop のチャットと Claude Code から検索できる。PyPI から入れたものでも動く

おもしろかったのは、**ページの間に索引が変わったとき**です。テスト用のファイルを置いて、ページとページの間に増やしたり消したりしてみました。

- ファイルを増やしたとき：新しいファイルは結果の最後に付き、ページはずれなかった
- 1ページ目に出ていたファイルを2つ消したとき：残りが2つ前に詰まり、**消していない2件が、どのページにも出なかった**

DSM の API には、ある時点の結果を固定して続きを読む仕組みがありません。なので、エージェントには「複数ページを合わせるときは `share_path` で重複を除く」「大事な検索は検索し直す」と伝えるようにしました。

## まだ確かめていないこと

- 90 日のセッションが終わりまでもつか（約 43 時間、200 回あまりの検索で失敗 0 までは確かめました。いまも続けています）
- Claude Desktop と Claude Code 以外の MCP アプリ（Cursor など）、アプリから数十秒以上かかる検索をしたときの動き
- ほかの機種・DSM のバージョン（まず `--check-api` で API があるか確かめてください）
- Universal Search 2.0（一部の上位機種だけ）

確かめた内容と、確かめていない内容は、リポジトリの `docs/verification.md` に分けて書いています。

## 使ってみるには

1. Universal Search で、検索させたい共有フォルダを索引の対象にする
2. 検索専用の DSM アカウントを作る
3. `unisearch` を NAS の `~/.local/bin/` に置いて、`--check-api` で確かめる
4. 人が検索セッションを始め、エージェントのマシンに `nas-search` と検索専用の鍵を置く（MCP で使うなら `uvx nas-search-mcp` で `nas-search` も一緒に入ります）

くわしい手順は README と `docs/agent-setup.md` にあります。
